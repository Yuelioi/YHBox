# V4 产品策略

## 结论

V4 的目标不是做一个功能更少的 Yotta，而是让高频任务更短、低频能力更安静、既有数据更可靠。
所有设计和重构都围绕三个词验收：

1. **简约**：默认界面只呈现当前任务需要的信息。
2. **快速**：已有 Workflow 可以直接打开或运行，配置只在真实缺失时出现。
3. **稳定**：升级不丢功能、不丢数据、不让旧 Workflow 突然失效。

同类产品的官方资料对照与适用边界见
[comparable-product-patterns.md](comparable-product-patterns.md)。本策略只吸收其中与本地个人自动化相符的
模式，不照搬企业发布、审批或市场安装流程。

## 当前问题

### 产品层

- 工作流首页同时承担浏览、搜索、分类、标签、日期筛选、排序、列配置、批量编辑、导入导出、替换、
  删除和损坏恢复，主任务与管理任务没有层级。
- 编辑器顶栏同时展示定位、AI、Run 状态、编译、时间线、调试、运行和设置；左侧、右侧、底部也同时
  展开，画布不是唯一视觉中心。
- 资源和 Schedule 页面沿用管理后台式布局，能力完整但首次使用成本偏高。
- 内部术语仍进入部分文案，例如 digest、immutable、installation settings，增加了无效学习成本。

### 代码层

- `WorkflowsView.vue` 约 1,500 行，页面同时拥有查询、筛选、选择、批量操作、导入导出、恢复和运行状态。
- `WorkflowEditorView.vue` 约 4,500 行，页面协调器知道过多工具、面板和运行细节。
- `AssetsView.vue` 约 1,800 行，资源浏览与资源管理没有清晰的任务 seam。
- 后端 `Application` 已经形成共享运行深 Module，但 presentation 仍把大量低层动作直接并列给用户。

## 产品定位

Yotta V4 是一个本地优先的可视化自动化工作台。

- 主要用户：为自己构建自动化的个人用户、开发者和高级玩家。
- 核心任务：找到 Workflow、编辑 Workflow、运行 Workflow。
- 次要任务：配置 Target、安排 Schedule、管理 Resource、查看 Run。
- 非目标：企业发布审批、作者信任仪式、软件市场安装状态机、远程策略控制。

## 心智模型

用户只需要先理解一个对象：

**Workflow**：可以编辑和运行的自动化。

其他概念按需出现：

- **Target**：Workflow 需要操作的本机应用、窗口、设备或服务。
- **Schedule**：让 Workflow 自动运行的可选触发方式。
- **Resource**：Workflow 使用的图片、录制和素材。
- **Run**：一次运行的状态和结果。

Resource 和 Run 不作为首次使用的前置知识；Target 和 Schedule 也不阻塞浏览与编辑。

## 信息架构

### 全局

- 工作流：默认入口和主工作区。
- 资源：支持工作区。
- 计划：支持工作区。
- 设置、启动器和关于：工具入口，不与主工作区争夺导航层级。

### 工作流首页

默认模式只包含：

- 页面身份和 Workflow 数量。
- 一个“新建工作流”主操作。
- 一个搜索框。
- Workflow 列表；整行打开，独立运行按钮。
- 有真实损坏项时显示一条可展开的恢复通知。

管理模式包含：

- 分类、标签、日期、排序和列配置。
- 多选、批量元数据、批量导出和删除。
- 导入、导出、替换等文件管理动作。

管理模式不删除能力，只把它们从默认路径移开。

### 编辑器

默认层级：

- 中央：Graph 画布。
- 顶部：返回、Workflow 名称、撤销/重做、保存状态、运行。
- 左侧：按任务切换的子图、录制、模板、Macro、Snippet、Resource。
- 右侧：只在选中对象时显示 Inspector。
- 底部：只在有问题、运行或用户主动打开时显示诊断、日志和时间线。

调试命令只在调试模式出现；AI 作为一个辅助入口，不与保存和运行并列成多个常驻按钮。

## 关键用户旅程

### 启动已有 Workflow

1. 打开 Yotta。
2. 从最近或搜索结果找到 Workflow。
3. 点击运行。
4. 若条件齐全立即运行；若缺配置，只显示缺项和修复动作。

验收：正常路径一次点击，无授权、安装或确认 Modal。

### 编辑已有 Workflow

1. 点击 Workflow 行。
2. 编辑器恢复上次视图或定位到主图。
3. 修改并保存。

验收：打开无需先理解版本、来源、资源摘要或运行配置。

### 新建 Workflow

1. 点击新建。
2. 输入名称，可选模板。
3. 直接进入编辑器并出现明确的“添加第一个节点”入口。

验收：名称是唯一必填项；分类、标签和高级元数据不阻塞创建。

### 配置并运行

1. 用户从任意运行入口启动 Workflow。
2. 系统给出统一 Readiness 结果。
3. 缺 Target 或 Credential 时就地选择或创建。
4. 修复后从原位置继续运行。

验收：配置属于当前设备，不改写 Workflow，也不产生第二类 Workflow。

## 交互规则

- 一个页面最多一个高强调主按钮。
- 正常路径不用 Modal；Modal 只用于创建、破坏性确认或需要完整上下文的编辑。
- 默认不展示高级筛选、批量工具、内部摘要和修订号。
- 用户动作使用结果语言，例如“缺少窗口目标”，不用机制语言，例如“admission denied”。
- Toast 只报告瞬时结果；可修复问题留在发生位置。
- 空态同时说明下一步，但最多提供两个动作。
- 动效用于载入、展开、运行状态和面板切换，尊重 reduced motion。

## 架构方向

### 保留的深 Module

- `Application`：所有 GUI、CLI、Schedule 和启动器运行的唯一入口。
- Workflow compiler/runtime：Source 到 Program 再到 Run 的唯一执行路径。
- Editor Session：Source 编辑、历史、命令归约和保存冲突的前端深 Module。
- Storage Root/Catalog/Blob：用户数据的一致性域。

### 需要深化的 presentation Module

- Workflow Library：对外只表达浏览、创建、打开、运行和进入管理模式；查询、恢复、批量和文件操作留在
  Module 内部。
- Run Readiness：所有运行入口消费同一种结果，不在各页面复制缺项判断。
- Editor Workspace：页面协调器只组合画布与任务面板，不直接拥有每个工具的细节状态机。

### seam 规则

- 真实存在 production/test 或多平台变体时才建立 adapter seam。
- 仅有一个实现的内部细节不暴露 interface。
- presentation 重构优先替换现有浅层，不叠加 V4 wrapper。
- 每个切片删除被替代的旧测试和旧路径，测试改从 Module 的用户可观察 interface 验证。

## 稳定性策略

### 能力不丢

- 以功能保留基线逐项核对，不凭文件是否还存在判断能力是否保留。
- 每个切片在开始前声明“默认隐藏、移动、重组、删除”中的哪一种；只有明确无调用且无用户价值时才能删除。

### 数据不丢

- Product Version、Workflow schema、Schedule schema、Run schema 和存储 layout 独立演进。
- 持久化迁移先验证候选，再原子发布；失败保留旧数据和恢复入口。
- 真实 `fishing-v2` 与 Blob 是长期黄金样本，不进入 Git，但本机验收持续使用。

### 行为不漂移

- 同一 Workflow 从列表、编辑器、Schedule 和启动器运行时走同一 `StartRun(workflowID)`。
- 内置节点契约修订只有在配置、绑定和拓扑可无损保留时自动迁移。
- 关键用户旅程使用 WebView smoke，而不是只验证组件快照。

## 量化验收

- 启动后无需配置即可进入 Workflow 首页。
- 已有 Workflow：一次点击打开，一次点击运行。
- 工作流默认页：一个主按钮、一个搜索入口、无常驻高级筛选和批量工具。
- 编辑器默认顶栏：不超过五组主任务；调试动作不在普通模式常驻。
- 正常运行：零确认 Modal。
- 旧 profile、`fishing-v2`、Source/Blob/Schedule/Run/Settings 继续可读。
- 每个阶段通过增量门禁；发布前通过 production build 和完整 WebView 旅程。

## 实施顺序

1. 先重做工作流首页，因为它是每次启动的入口，也是当前最明显的管理后台化页面。
2. 再统一 Run Readiness，打通“运行时才配置”的核心承诺。
3. 然后聚焦编辑器，把复杂能力按任务重组。
4. 最后处理资源、计划、设置和性能，完成整体一致性。

不同时大改数据模型、执行引擎和全部页面。每个阶段都必须可独立使用、验证和回退。
