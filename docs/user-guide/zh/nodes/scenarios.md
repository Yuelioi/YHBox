# 节点使用场景

复杂工作流不应从“有哪些节点”开始设计，而应先确定触发条件、成功证据、失败处理和停止方式。下面的示例
使用节点职责描述连接方式；具体字段以编辑器当前显示为准。

## 场景一：每隔一段时间检查条件

适合等待页面状态、轮询接口或监测目标程序。

```text
Run 开始 → 循环 → 执行检查 → 分支
                  ├─ 满足 → 中断循环 → 后续操作
                  └─ 不满足 → 延迟 → 继续下一轮
```

关键点：

- 延迟放在“不满足”路径，避免无间隔占用 CPU 或频繁操作目标。
- 给循环设置合理上限；需要长期运行时仍应保留可取消点。
- “暂时不满足”通常属于状态，不应该直接抛出错误。
- 真正的目标丢失、输入失败或配置错误应进入错误路径并留下 Run 证据。

## 场景二：点击后恢复鼠标位置

适合天赋树、确认按钮或其他不希望改变玩家鼠标落点的操作。

```text
Run 开始 → 读取鼠标位置 → 移动到目标 → 点击 → 移回保存的位置
```

位置读取和恢复必须使用相同的坐标空间。目标窗口可能移动时，优先保存窗口客户区比例位置；明确要恢复桌面
光标时才使用屏幕绝对位置。点击或移动可能失败的节点应连接错误路径，避免流程中断后鼠标停在错误位置。

## 场景三：播放可编辑的键鼠宏

适合一组固定点击、按键、滚轮和等待，并且希望以后逐条修改。

```text
Run 开始 → 激活目标窗口 → 播放宏 → 检查结果/继续流程
```

- 录制时只保留必要动作，删除误触和过长等待。
- 点击位置变化时，在宏编辑器里调整坐标或重新录制。
- 宏包含窗口相关坐标时，播放前先确认目标客户区分辨率。
- 不要在宏外再重复添加相同按键，否则可能造成双击或状态翻转。

## 场景四：播放精准鼠标轨迹

适合拖拽、绘制、连续移动或游戏视角转动。

```text
Run 开始 → 激活目标窗口 → 应用鼠标校准 → 播放精准录制 → 后续操作
```

相对鼠标轨迹依赖 360° counts。不同游戏、不同游戏内灵敏度或不同电脑应使用对应校准档。保存前裁掉无关的
开头和结尾；裁剪边界落在按住区间时，Yotta 会补齐按下与释放，避免回放后卡键。

## 场景五：根据结果走不同路径

```text
上游节点输出数据 → 比较/判断 → 分支
                              ├─ true  → 成功路径
                              └─ false → 备用路径
```

分支只负责选择路径，比较规则应放在独立数据节点中。这样运行时间线能分别显示“数据如何得到”和“为什么选择
这条路径”，调试时更容易定位问题。

## 场景六：可安全停止的长流程

长流程应由多个可取消的小步骤组成，而不是一个无法观察的大动作。循环、延迟、输入播放和目标操作都会接收
Run 取消信号。为按住键或鼠标按钮的流程使用输入租约，确保正常结束、错误和用户强停时都能释放输入状态。
