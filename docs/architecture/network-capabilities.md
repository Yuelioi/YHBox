# Installed network capabilities

Yotta does not expose an ambient HTTP client. `internal/httpegress` seals each permitted origin into an immutable installation profile containing the exact scheme, host, optional port, private-network policy, response byte limit, and wall-clock timeout. A Node Contract selects only a logical installation slot; workflow data can contribute a relative path and a bounded query object, never a scheme, authority, proxy, redirect policy, credential, cookie, or request header.

The startup composition freezes installations into the Host Profile, provider inventory, target-slot bindings, and built-in Policy. `HTTP GET` declares one sensitive `ConsentOnce` capability and cannot receive a Run Grant until the exact slot/profile consent digest is present. Any semantic profile edit revokes the persisted consent. Because Host Profile and providers are startup snapshots, installing, editing, granting, or revoking an origin takes effect after restart; there is no live fallback provider.

The provider constructs the final URL by copying the installed origin and assigning a validated absolute path plus canonical query encoding. Redirect following and environment proxies are disabled. DNS is resolved inside the provider, every result is checked, and the transport dials a validated numeric address while retaining the original hostname for HTTP/TLS. Public-origin profiles require HTTPS and reject loopback, private, link-local, multicast, unspecified, carrier-grade NAT, and benchmark networks. A separately consented `allowPrivateNetwork` profile may reach loopback/private addresses but still rejects link-local, multicast, and unspecified destinations. This follows the allowlist-first and redirect/DNS controls recommended by the [OWASP SSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html).

Responses are limited after content decoding, must be UTF-8, and expose only status code, body, and content type. `Set-Cookie` and all other response headers stay outside workflow data. The adapter records status and byte counters plus a relative-path digest; it does not journal the URL, query, body, or response text. The reusable `http.Client` has an explicit total timeout and redirect callback, and response bodies are always closed, matching the relevant [Go `net/http` client requirements](https://pkg.go.dev/net/http).

Additional network operations are new contracts, not flags on `HTTP GET`. Authentication, request bodies, custom headers, binary responses, streaming, and WebSocket sessions require their own capability scope, credential binding, data carrier, budgets, consent identity, provider operation, action summary, and generated documentation. This keeps the current GET authority narrow and makes future review mechanical.
