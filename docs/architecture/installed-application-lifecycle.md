# Installed application lifecycle

Yotta does not expose a generic command, executable path, argument string, working directory, environment, PID, URL, or document opener. Desktop application automation uses capability `https://schemas.yotta.dev/capabilities/application/lifecycle/v1` and binds one logical slot to a user-authorized installed profile.

The trusted profile contains an absolute `.exe` path and a fixed list of argv elements. Shells, PowerShell, script hosts, batch files, file associations, `PATH` lookup, raw command lines, and workflow-supplied arguments are rejected. Yotta's own host executable is also rejected, so a workflow cannot launch or terminate another Yotta instance through this authority. SHA-256 is an inspection observation, not the durable application identity: a normal software update at the authorized path does not revoke the profile or workflow consent. Installation does not touch the external file, so one missing application cannot prevent Yotta from starting; every invocation still requires the path to resolve to a bounded regular `.exe`.

`Launch installed application` has only `in`, `completed`, and `failed` signal ports. It intentionally has no generic `out` or workflow-visible process identifier. `Terminate installed application` additionally returns `terminated-count`; the Windows provider enumerates processes, opens a process handle, resolves its executable, and terminates it only when the OS file identity matches the currently authorized path. It does not accept names, wildcards, arbitrary PIDs, or invoke `taskkill`.

The capability is `dangerous` with explicit `ConsentOnce`. Admission locks the exact target, provider artifact, capability scope, Program, Run, node, and operation before an effect occurs. Changing the authorized path or fixed arguments revokes consent; replacing bytes through a normal update at the same path does not. Action journals record only stable operation outcomes and non-secret counters such as launched or terminated count; executable paths, argv, PIDs, environment, and user data are excluded.

This provider is not a sandbox. A trusted GUI application is expected to run with the current desktop user's authority so it can participate in desktop automation. Its child environment is reduced to a fixed set of operating-system directories and excludes inherited `PATH`, proxy, token, and arbitrary Yotta variables, but the application can still use the user's files, registry, network, windows, and credentials through normal OS APIs. The installation/consent boundary controls which trusted application a workflow may trigger; it does not make that application untrusted code.

Third-party nodes, CLI data processing, and AE/UE adapter workers are a different `Process Node`/Plugin Host boundary. They must use a content-addressed package, typed operation protocol, LPAC/AppContainer, atomic Job Object association, exact inherited handles, resource budgets, and fail-closed host-feature admission. They must never reuse this desktop lifecycle provider. Linux and macOS expose the contracts for authoring but do not install the lifecycle provider until an equivalent implementation exists; there is no weaker subprocess fallback.
